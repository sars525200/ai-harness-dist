# 2026-09-08 新增（首次盤點跨對話通訊工具）：
#   這台機器上同時存在兩套獨立的對話間通訊機制，各自的定址方式、涵蓋範圍、
#   收件人限制都不同，混用會送錯或送丟。查證過程：實際呼叫兩邊各自的清單工具
#   （`list_sessions`／`ListAgents`），逐一核對 10 則對話的 id，證實兩套 id
#   命名空間互不相通（見 `21-title-claude.md`）；接著實際送過一次測試訊息，
#   證實「送出成功」不等於「對方已讀」——工具回報對方可能卡在等 approval，
#   側邊欄也不會顯示任何未讀提示，要確認送達得回頭讀對方的逐字稿。
#   為什麼放這裡不放常駐層：這兩點是「用這兩顆工具時要知道的細節」，常駐層
#   只留「送之前要查表確認、送了不代表對方看到」這種做什麼／不做會怎樣。
---
- **兩套通訊系統不互通，定址方式各自查各自的清單**：
  - CCD 桌面對話：`mcp__ccd_session_mgmt__send_message` 配 `list_sessions`／`get_session`，
    用完整 `sessionId` 定址。
  - 通用的（含 subagent／teammate／Remote Control／雲端）：`SendMessage` 配 `ListAgents`，
    用清單裡的名字／ref 定址。
  兩邊的短碼互不相通，細節見 `21-title-claude.md`。**送之前一律先查對應清單確認目標**，
  不要拿標題、記憶裡的舊 id 或猜測直接送；關鍵字撞到兩則以上，列出來讓 user 選一則。
- **送訊息屬於代 user 發訊息**：每次要送都在對話裡明講目標＋內容、等 user 確認才送，
  不能因為同一則對話之前送過一次就當作後面都不用再問。
- **無人值守的對話送不到**：排程跑的、遠端派發的收不到，`SendMessage` 本身會直接拒收；
  硬要送等於白做。
- **送出成功不等於對方已讀、更不等於同步**：對方要醒著才會處理，工具回報「已送達」時
  可能只是排進對方的等待佇列（例如卡在 approval 畫面）。側邊欄不會有未讀提示，
  **要確認送達得用 `list_events` 讀對方逐字稿**，不要假設送了就等於做完交接。
- **反過來看別人做到哪不用送訊息**：`list_events` 直接讀對方逐字稿即可，唯讀操作，
  不需要對方回應也不用另外問 user。
