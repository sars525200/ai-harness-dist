## 3. 工作流：Research → Design → Execute → Review → Fix

**跳過哪一階段就會在那一階段付代價。** 核心是交接：**下一棒不必回頭問上一棒就能開始工作。**
編排走 `/session-workflow`（步驟執行器；規則本體仍是本節）。

**先分級，再決定走多少**（判準是動工前可答的**事實**，不是「複雜不複雜」——要判斷的判準會被自我豁免）：

- **M 大型**＝資料遷移/DELETE・動角色·規則·hook・跨 repo・user 說「計畫書／大型」・預估跨 session
  → 五階段全走 ＋ **計畫書先行** ＋ 交付物**落檔**（落在該任務的計畫書，不新建交接檔）
- **S 標準**＝改 **≥3 檔**・碰硬規則區・改有多處副本的共用邏輯・要部署・要派 subagent
  → 五階段全走，交付物留對話但**欄位齊全**
- **L 輕量**＝以上都不命中 → Research 壓成一次 grep、Design 可省

判成 L 而實際改了 ≥3 檔時，**那行宣告自己就是證據**——**宣告的「規模」欄 vs 實際動的檔數，
兩欄一比就知道**，不靠自評。

**每階段交出什麼**（粗體＝必填的空缺欄，留空會被下一棒讀成「已窮盡」；**寫「無」也比留空好**，
「無」是一個判定、留空是一個未知）：

| 階段 | 交付物 | 必填欄位 |
|---|---|---|
| Research | 研究資料包 | 命中（`檔:行`）／已排除／**沒找到的** |
| Design | 工作規格 | 做法／待決分岔（選項＋傾向＋理由）／**驗證方式** |
| Execute | 改動對照 | 改了什麼／為什麼是這個值／**沒做的＋理由** |
| Review | 判定＋證據 | 逐項判定／每項的實跑指令·量到的數字·截圖／**未驗項四欄** |
| Fix | 修復對照 | 發現 → 改動 → 怎麼驗／每條標 fixed 或 skipped＋理由 |

### Research

**開場必派**：評估規模後立刻派查詢員＋規劃，不必等人點名；動代碼前先讓唯讀角色盤過。
L 級可壓成一次 grep。**派誰＝哪個平台哪個型別見 skill 步驟 1。**
重點不在派不派，在**查得準 ＋ 查不到要疊代**：

1. 查詢範圍隨難度升層：因果 → 結構 → 環境
2. **回報「都正常」而問題仍在＝查錯方向的訊號**，換角度重派，
   **禁把它當答案繼續猜**（曾經接受了第一次的「都正常」而多猜三輪）
3. 每輪帶入上輪已排除項，不重查同一片

**改前先 grep 找齊全部 copy**：同一份邏輯常有多處副本（雙份目錄、client/server 鏡像、
常數與寫死值）。只改一處等於沒改，而且**不會報錯**。

### Design

**大型工作計畫先行**：M 級**先寫計畫書**（現況 → 目標 → 做法 → 驗證 → 狀態）→
逐項討論 → **同意才執行**。連非破壞性的 infra 改動也要先講。
**驗證方式在動工前就要寫好**，不是做完才想怎麼驗。

### Execute

照規格做，**不擴張範圍**。

**中途撞到別的問題，判準是「不修的話我的完成回報會不會是假的」**（不是「是不是主線」）：

- **會**（測試自己洗綠／驗證照不到要改的那行／守門擋不住它宣稱擋的東西）→ 當場修，交付時列為附帶修正。
- **不會** → **記票不修 vs `spawn_task` 二選一（2026-09-06 定）**：先判斷能否**獨立成一個任務**
  （脫離這則對話脈絡也做得下去）——能 → 呼叫 `spawn_task` 產生建議任務卡；
  不能（單純分心小事、離不開這則脈絡）→ **記票不修**。三行：發現什麼／不修的後果／
  **可直接貼的分支指令**。落點用現成的（`.scratch/<主題>/issues/NN-*.md`、`TODOS.md`、待驗清單），
  **不新建**。**不重複登記同一件事**——選了 `spawn_task` 就不再寫進 issues 檔。
- **只在回覆裡講一句不算記票**——關掉對話就沒了，等於沒發現。

**完成判準**：交付時對每個繞路講得出「不修會怎樣」。講不出來＝那是分心，當初該記票。

### Review

**回退**：**禁把作法錯誤當 Fix 硬改**（回哪一步見 skill 步驟 4）。**碰高風險改動主動問要不要跑
`/adversarial-review`**（判準見該 skill 的 description，不重複抄在這裡）。

**驗證紀律**：`node --check` 這類語法檢查**只驗語法不驗執行期**；
重構分支必真實執行；測試全綠但使用者說沒好 → 先懷疑測試而不是使用者。
**新寫的驗證預設它自己有問題——先證明它會紅，再信它的綠。**

**寫守門時，判準綁後果、不綁名字**：靠變數名或檔名認違規＝要預測下一個人怎麼命名
（2026-09-05 實測：只命中 7 個缺口中的 1 個）。綁後果則合法的自動放行、不必養白名單。
**而「永遠紅的守門」等於沒有守門**——判準寬到把會吵的缺陷也收進來，人就不讀輸出了。

### Fix

收斂到「**已修且已生效**」，不是「已知道」（怎麼驗見 skill 步驟 5）。

### 交接契約（跨階段三條硬規則）

1. **交付物要能脫離對話存在**——貼進一個新 session 也讀得懂。這是「換人接手」的最低標準。
2. **「沒做的／沒找到的」是交付物的一部分**，不是可選欄位。
3. **跨階段不繼承推測**。上一棒的推測要標成推測；下一棒**不得把推測當事實往下傳**。
