計畫＝計畫書表格裡狀態標在格首的未結案列；粗抓＝散文型待辦檔的 bullet。這兩類只當指路用——判準是量出來的（放寬版抓 20 列、一半是方案比較表與文件清單，收緊成「狀態必須在某一格開頭」才降到 8 列），仍可能抓到不精準的東西，所以每項都附來源檔與行號，動工前先開來源檔確認。

要新增一個專案的待辦：在該專案 .claude\PROJECT_CONTEXT.md 補「待辦來源」表。沒填就是沒有——產生器不會去猜哪個檔像待辦清單。

優先程度：手填優先，沒填才推導。來源表加一欄「優先」（填 高／中／低）就以它為準；沒填的由「誰跑」推導——高＝本 session／下一輪／下次開場這種馬上要動的，中＝有明確觸發條件但在等（等真機、等排程、等人），低＝沒有觸發條件（未排程／待決定），粗抓兩類預設低。畫面上推導出來的會標「（推導）」，不假裝是人定的。

時間＝來源檔那一行最後被寫入的時間（`git blame`），不是「最初加入」——後者要逐項掃 git log，對上百項來說太貴。同一列被編輯過，時間就會往前跳，那是正確的語意。

做完就把來源檔那一列刪掉，不留「已完成」歷史（那是 git log 的職責）。看板下次重生就會少一項。

角色能力邊界

code 在哪跑、能摸到什麼 · 由 agents/*.md 的 frontmatter 決定

每個角色能用哪些工具寫在自己的 tools: 裡；三個稽核／檢核角色的 Bash 另外被 agent-scoped 閘門收窄成唯讀。那個閘門掛在角色檔的 hooks: frontmatter， 不在 settings.json —— 找錯地方會以為它根本沒接（2026-08-06 差點誤報）。

※稽核者唯讀是刻意的——稽核者能改被稽核的東西，會讓漂移從此不再被記錄。 有寫入能力的是兩個：美編人員的 Bash 不掛角色閘門、只受全域 dispatch 管； 施作員則刻意連 Bash 都沒有——白名單擋不住 python x.py 裡的 git push， 所以改成能力不存在，驗證與部署留給下一棒。

HARNESS_PLAN.md §-0.5 長期把「exit 2 到底擋不擋得住、訊息餵不餵得回模型」列為未驗項，理由是「hook 是專案層級，測 exit 2 會擋到其他並行 session」。這個理由把方向搞反了：正因為是專案層級，另開一個 cwd 放自帶的 .claude/settings.json 就完全隔離。
探針手法：第一次 Stop 回 exit 2、stderr 塞「請原樣輸出暗號 ACK-7F3A-CONFIRMED」——輸出裡有暗號＝既擋住了、也讀到了，一次驗兩件事

四點結論

  1. exit 2 真能擋住 Stop — 模型本來已輸出「完成」要結束，被逼著再跑一輪。
  2. stderr 全文真的餵回模型 — 含中文，指示被完整理解。
  3. stop_hook_active 可靠 — 被擋後那輪確實為 true，可安全當防迴圈欄位。

Eval 為何這樣設計（結論可抄，理由才可遷移）

先定義它會怎麼壞（四種失敗），為每種建立可檢查的判準——而不是先蓋一套 eval 平台。10 支 skill 的規模撐不起平台的維護成本，那正是 hook 層剛否決過一次的判準。

  • 型別skill 有兩種，判準必須分開。license-rules 的 0 步驟 0 完成判準不是缺陷，它是刻意的參考資料型。用流程型判準測它會產生假 FAIL，而假 FAIL 會讓人開始無視整套 eval——比沒有 eval 更糟。
  • 塞爆判準不能照抄 CLAUDE.md 的防膨脹量測。CLAUDE.md 是 always-loaded、每則對話都付，才有 120 字硬上限；skill 是 on-demand、只在被觸發那次付一次 → 單支大不是罪，真正的浪費是「與記憶檔重複」＝同一份知識付兩次錢。
  • 過期用「檔案改動 or 契約失敗」，不用日曆天數。沒改過的 skill 不會因時間流逝而失效；會失效的是它的依賴，那由 L2 抓。日曆天數會對穩定的 skill 產生週期性假警報。
  • 誠實執行面不假裝能自動化。實跑品質要人判斷，所以降級成可自動追蹤的元資料——記錄上次實跑時間與之後有無改動，把無法自動化的部分變成「該不該重跑」的訊號。
※run_all.py 的 PASS 不包含「skill 實際跑起來對不對」——L3 評分要開 subagent、L4 實跑要人在場判斷輸出品質。沒有硬串成自動，那只會生出「看起來全跑過」的假象。

三個假綠燈，全都是 eval 自己的問題沒有一個是被測對象的錯
同一天蓋四層，三層各自在第一次跑就現形一個假象。這是本輪最大的收穫，也是為什麼每個偵測器都必須配 self-test。
  1. L1 重複偵測恆為 0% — 拿「清洗後的片段」比對「未清洗的 corpus」，兩邊正規化不一致 → 永遠對不上。靠 self-test 塞 5 句記憶庫原文、一句都沒抓到才揭穿。沒有 self-test 就會一直以為「沒有重複」。
  2. L2 首跑 8 個 MISSING 全是假 FAIL — 路徑 base 不足、/api 被當 skill 引用、YYYYMMDD 佔位字串被當真實檔案。修完之後又發現我把檢查改成了恆真（只驗清單內的，那當然都存在）——修假警報的過程中親手造出第二個假綠燈，再改成「不報 FAIL 但揭露」。
  3. L3 的 4 個誤觸有 3 個是題目出錯 — 期望值標錯（「資料不見了」本來就該走 data-incident，我卻標成 none）、語意模糊、同一句寫進兩個檔案只改一邊。紀律：改期望值必須因為題目本身錯，不能因為模型答不出來就改題，否則 eval 當場失去意義。
通則：新建的 eval 第一次跑，預設它自己有問題。先證明它會叫（self-test 正反兩向：必定命中的資料要抓得到、純乾淨資料不得誤報），再相信它的「全綠」。
