# 對抗式方案覆核（/adversarial-review）

> 本 skill 是 CLAUDE.md §2「大型工作計畫先行」的**覆核層**——那條規則要求先寫計畫書、逐項用選擇題討論；本 skill 提供「逐項討論」的另一個選項：找一個真正獨立的審查者，不是我自己左右手互搏。碰 [DB｜邏輯] 類（§7 既有分類）的大型計畫，主動問 user 要不要跑一輪。

## 前提

要有一份計畫文件（`*_PLAN.md` 或等效）已存在——本 skill 不取代寫計畫書那一步，只在計畫書之上加一層獨立驗證。沒有計畫文件先照 §2 寫一份。

**wayfinder 規劃圖（`.scratch/<effort>/map.md`）也是合法的審查對象**（2026-08-22・分岔 1 C＋D／K14）。差異只有兩處，其餘步驟照走：
- **審查範圍**＝map 的 Destination／Notes／驗證方式／Out of scope（`REVIEW_SCOPE_IGNORE` 區內的 Decisions so far／Not yet specified 是每票例行 append，不在審查範圍）。審查者可自行 Read 各 child ticket 補脈絡。
- **步驟 4 的「vN 版號」對 map 改記在 IGNORE 區內**：map 沒有版號慣例，變更紀錄表 append 在 `## Decisions so far` 之後（同在 IGNORE 區），一樣要「意見 → 處置」逐列可回溯。審完在**檔尾**蓋 `ADVERSARIAL_REVIEW_PASSED` marker（hash 算法同 PR-1，重算指令見 PR-1 的 BLOCK 訊息）。
- **多 session 併行時 marker 要蓋兩個 hash**（2026-08-22 起）：`sha256=` 是蓋章當下的現況，`reviewed=` 是**派出審查者的那一刻**算的 hash。做法＝派審查者之前先算一次記下來，蓋章時一起寫進去：

      <!-- ADVERSARIAL_REVIEW_PASSED sha256=<現況> reviewed=<派審查者當下> rounds=<N> at=<ISO> -->

  兩者不同 PR-1 就擋，因為那代表**覆核期間有人動過審查範圍**，而那個改動沒被審過卻會跟著憑證被當成已審（實測可重現）。舊 marker 沒有 `reviewed=` 照舊有效，不必回頭補。單一 session 獨占時兩個值本來就相同，多寫一欄的成本接近零。

## 步驟

### 1. 決定審查者——讀設定檔，不要自己挑

**先讀** `D:\.ai-harness\reviewer\reviewer_config.json`（2026-07-31 起，原本是寫死「Codex 優先」）：

```
py -3 D:\.ai-harness\reviewer\server.py --check
```

它會印出目前設定與**每個工具在這台機器上裝了沒**。三個欄位：
`tool`（`claude-code`／`cursor`／**`cursor-cli`**／`codex`）、`effort`（`high`／`medium`／`max`）、
以及 `model` —— **`model` 的合法值依 `tool` 而定**（2026-08-25 起）：
- `claude-code` 吃抽象檔位：`inherit`／`opus`／`sonnet`／`fable`
- **`cursor-cli` 吃 Cursor 自己的 model slug**（`cursor-grok-4.6-xhigh`、`gpt-5.3-codex-xhigh`…），
  那是開放集合（Cursor 改版會增減）⇒ 不在推薦清單的 slug **只提醒、不讓 `--check` 失敗**。
- `cursor`／`codex` 的 `supports_model` 是 `False`，`model` 那格對它們是空轉的。

**⚠ 先看 exit code，不要只讀畫面**（2026-08-25 起）：`--check` 在**未知設定值**、
**檔案不存在**、**JSON 壞掉**、**欄位缺失或是空字串**時都會 **exit 2** 並印 `✘`。

**看到非零就停下來問人。不要自己挑一個分支繼續。**

⚠⚠ 這裡**不再有**「讀不到檔就用預設 `claude-code` 並說出來」那條退路（2026-08-25 覆核 R2-2 移除）。
那句話與 exit 2 直接打架，而且合起來剛好授權你：`--check` 紅了 → 依那句改派 Claude →
講一句「檔讀不到我改用預設」→ 蓋章。**那正是這支 skill 要防的事，只是披了合規的外衣。**
設定壞掉時正確的行為是**停**，不是換人——因為「預設」就是 `claude-code`，
而你就是 Claude。

- **`claude-code`（預設）** → `Agent` tool 開一個 `subagent_type: "Plan"` 的獨立 subagent，
  帶上設定的 `model` 與 `effort`（`inherit` 就不傳 `model`）。選 Plan 型是刻意的：
  它有 Read/Grep/Bash 可以查證，但沒有 Edit/Write——符合「審查者只能挑錯、不能動手改」的邊界。
  ⚠ 它與你同一個模型族，**共享盲點**。有 `cursor` 可用時它是次選，不是首選。
- **`cursor`** → **落檔交換**（人工通道，見步驟 1b）。程式叫不到 Cursor
  （`ListAgents` 看不見它），所以你寫題目檔、**停下來請人貼進 Cursor**、
  等回覆檔寫回來再繼續。**這是這台機器上唯一真正跨模型族的審查者。**
  ⚠ **不要用 `shutil.which("cursor")` 判斷它可不可用**：2026-08-25 實測，
  同一個判準在 Cursor 自己的 process 有值、在 Claude 這側是 `None`——答案取決於誰在問。
  ⚠ **另有 `cursor-cli` 全自動通道（步驟 1c）。** 設定值是 `cursor` 時走 1b（人工貼），
  是 `cursor-cli` 時走 1c。**設定要哪個就走哪個**——CLI 繞過了 1b 那條
  「人親手貼過一次」的防線（那是唯一能分辨「真的有外部審查者」與「自己代筆」的東西），
  **不得自己判定改走 CLI**，除非人明說。
  ⚠⚠ **`cursor` 根本沒有「不可用」這個狀態，只有「還沒回」**（覆核 R1-4／R2-6）。
  不要把「這一輪還沒有回覆檔」讀成「Cursor 不可用」然後套用下面那條「不可用就換人」——
  人還沒貼之前它永遠是那個樣子，那樣等於自動獲得換人的授權。**還沒回就是等。**
- **`cursor-cli`（2026-08-25 新增·跨模型族且全自動）** → 直接跑 Cursor 官方 CLI，
  一輪從頭到尾沒有人工步驟。**它是 `cursor` 的升級路徑**：同樣跨模型族，但不必有人當傳話筒。
  詳見步驟 1c。
- **`codex`** → 先確認裝了沒（`--check` 會告訴你）。有裝就用非互動模式跑，跑之前先
  `codex --help` 或 `codex exec --help` 確認實際參數，不要憑記憶猜旗標（CLI 版本間常改）。
  **沒裝 → 改用 `claude-code` 並明講你換了**（見下）。

### 1b. `cursor` 的落檔交換協定

設定是 `cursor` 時，步驟 2 的 prompt **不是**丟給 subagent，而是**寫成檔**：

| 檔 | 誰寫 | 規則 |
|---|---|---|
| `<effort 目錄>/round-N-ask.md` | 你 | 寫完**就凍結**。要改題目請開 `round-(N+1)-ask.md`，**不要改已派出的檔** |
| `<effort 目錄>/round-N-reply.md` | **Cursor** | 你**不得自己寫這個檔**。見下方「已知上限」 |

四條硬規則（缺一就等於沒覆核）：

1. **ask 寫完即凍結**——派出前跑：

   ```
   py -3 D:\.ai-harness\tools\adversarial_exchange_gate.py --stamp-ask <round-N-ask.md>
   ```

   它會在檔尾寫入 `ask-sha256=`。之後**不要再改這個檔**；要改題目請開下一輪的 ask。
   PR-1 的 `reviewed=` 只綁**被審那份計畫文件**的審查範圍，**ask 被改到它完全看不見**。
2. **reply 檔頭必須帶回同一個 `ask-sha256=`**。對不上＝這份回覆不是針對派出的那題，當沒回覆
   （最常見的成因是複製了上一輪的 reply）。
3. **reply 必須有非空白的發現區。**「沒有發現」也要明寫那句話並說明查了哪些地方。
4. **蓋 marker 之前**跑守門，並把**輸出與 exit code 一起貼進回報**：

   ```
   py -3 D:\.ai-harness\tools\adversarial_exchange_gate.py --check <effort 目錄>
   ```

   它掃**每一輪**（不只最新那輪，否則「跳過中間某一輪」會靜默通過），
   任何一輪缺 reply／hash 對不上／發現區太空 → **exit 2**。
   **非零就不准蓋 `ADVERSARIAL_REVIEW_PASSED`。**

**⚠ 已知上限，必須照實說**：檔案系統上「你自己 Write 一份 reply」與「Cursor 真的寫回」
**完全同形**，沒有機器能分辨。這個機制**防遺忘、不防作弊**。
唯一的真防線是「**人親手貼過一次**」——所以設定是 `cursor` 時你**必須停下來等人**，
不得因為「先自己審一輪比較快」就跳過。

**⚠ 換人一定要說**：設定指定的工具不可用時，照實回報「設定要 X，這台機器上找不到，改用 Y」。
**「以為找了外部 AI 覆核、其實是自己審自己」比沒覆核更危險**——那會讓一份沒被真正挑戰過的計畫
帶著「已覆核」的標籤過關。

**⚠⚠ 但「不可用就換人」這條 `cursor` 不適用**（2026-08-25 覆核 R1-4）：
`cursor` 的「可用」被定義成「這一輪有沒有合格的回覆檔」⇒ **人還沒貼之前，依定義永遠是不可用**。
兩條規則合起來，字面上會授權你「等不到就改派 Plan subagent，反正我有明講」——
那正好是這支 skill 要防的事，而且披著合規的外衣。

**所以：`cursor` 沒有「不可用」這個狀態，只有「還沒回」。還沒回就是等，不是換人。**
真的要換（人明說不等了），必須是**人下的指令**，不是你判的。

**要改設定**：`D:\.ai-harness\reviewer\Launch-Reviewer.bat`（本機設定頁 8899，**直接寫檔**）。
⚠ **不要走 harness 看板（8099）的選單**——**它存不了設定**，只能觸發瀏覽器下載或複製到剪貼簿，
真相永遠是本機那個檔。按了它的「下載」再手動覆蓋，等於用畫面上那組值蓋掉磁碟上的值，
而畫面預設勾的是 `claude-code`（＝自己審自己）。
（2026-08-25 訂正：舊版這裡寫「它的 radio 只有 `claude-code`／`codex`、沒有 `cursor`」——
**那句已過期**，看板 modal 現在有 `cursor`。不該走它的理由是「存不了」，不是「選項不全」。）

**完成判準**：把 `--check` 的**實際輸出與 exit code 貼進回報**，並講出這輪用的是哪個審查者、
哪個模型，以及**設定要的是不是就是這個**。
只寫散文「我用了 X」不算——散文可以假綠，exit code 不行。

### 1c. `cursor-cli` 的全自動協定（2026-08-25 新增）

設定是 `cursor-cli` 時，**不寫題目給人貼，直接跑 CLI**。一輪長這樣：

```bash
agent -p --mode ask --trust --workspace <隔離沙箱> --model <slug> "<prompt>"
```

`agent.cmd` 在 `%LOCALAPPDATA%\cursor-agent\`（安裝：`irm 'https://cursor.com/install?win32=true' | iex`）。
⚠ **安裝寫的是 User PATH，已開著的行程拿不到** ⇒ 用完整路徑呼叫，別依賴 `which`。

**四條硬規則**：

1. **`--workspace` 一定要指到隔離沙箱，不可以是本 repo。**
   CLI **會讀專案根的 `CLAUDE.md`、並從 `.claude/skills` 發現 skills**（官方文件明載）。
   在本 repo 直接跑 ⇒ 審查者載入跟作者同一套規則與技能，**「不共用推理脈絡」當場失效**，
   而且沒有任何訊號會告訴你這件事發生了。
   沙箱作法＝**乾淨目錄 ＋ junction 連要查證的程式碼目錄**，不連 `CLAUDE.md`／`.claude`：

   ```powershell
   New-Item -ItemType Junction -Path D:\reviewer-sandbox\SOP_PROD -Target <程式碼目錄>
   New-Item -ItemType Junction -Path D:\reviewer-sandbox\effort   -Target <effort 目錄>
   ```

   ⚠ 沙箱的**父目錄**也要乾淨（`D:\AI-Projects` 與 `D:\.ai-harness` 底下都有 `CLAUDE.md`）。
2. **唯讀靠 `--mode ask` 且不給 `--force`。** 給了 `--force` 它就能改任何檔——
   而 junction 指向的是真的程式碼目錄。
3. **要求它把回覆印到 stdout，由你落檔**（`--mode ask` 寫不了檔）。
   ⚠ **PowerShell `Out-File -Encoding utf8` 會加 BOM**，`ask-sha256` 檔頭會被守門認不出 ⇒
   落檔時用 `utf-8-sig` 讀、`utf-8` 寫。
4. **一律背景執行。** 實測一輪 10 分鐘以上（Grok xhigh），前景會撞工具逾時被砍，
   而且 `Out-File` **一個 byte 都不會 flush**——只留下一個 0 byte 的假 reply 檔，
   那東西會讓交換守門誤判成「有回覆」。

5. **prompt 不可含換行**（2026-08-26 實測）。Windows `.cmd` 包裝器會吃掉含換行的單一參數
   ⇒ **exit 0、stderr 空、stdout 只有 1 byte**。細節寫進 ask 檔，命令列只給一行
   「請讀 `<ask 路徑>` 並照它做」。
6. **`agent -p` 的退出碼完全不可信**（2026-08-26 實測）。成功回 0；把 26k token 的輸出
   **整份丟掉也回 0、stderr 也空**（176k input 的大型 run 發生過）。
   ⇒ 必加**產出大小守門**（`< 200 bytes` 就明說「等於沒跑」），再去
   `%TEMP%\cursor-agent-logs-*/` 最新 log 讀 `AGENT_TURN_OUTCOME` 分辨兩種情況：
   - 沒有 `outcome=success` → 真的沒跑，重跑
   - 有 `outcome=success` 且 `output_tokens` 非 0 → **跑了但 stdout 掉了**：
     從同一份 log 抓 `conversation_id`，`--resume <id>` 叫它把報告原樣再印一次（實測撈得回來）
7. **`--model` 先跑 `--list-models` 確認 id**，不要憑記憶猜。
   ⚠ 設定檔的 `model` 若是 `opus`，照字面會挑到 `claude-opus-5-thinking-high`——
   **與 Claude 同族、共享盲點**，抵消掉用 Cursor 的唯一理由。跨族請挑 grok／gpt 系，
   **並在回報裡明講你沒照設定檔走**。

⚠ **貼 exit code 時當心管線**：`cmd | tail` 之後的 `$?` 是 `tail` 的、不是守門的
（2026-08-26 實測踩過，害我一度回報「守門 exit 0」而它其實是 2）。

**落檔協定的差異（相對 1b）**：reply 檔由**你**從 stdout 落檔，不是審查者自己寫。
1b 那條「你不得自己寫 reply 檔」的用意是防「自己代筆假裝有人審過」，
在 CLI 模式下改由**更硬的證據**承擔：保留 `agent -p` 的**原始 stdout 與 exit code**
（`_rN_raw.txt`）。那是人工貼上做不到的稽核痕跡。
⚠ 但 `ask-sha256` 那行仍必須是**審查者自己輸出的**——
你只做編碼轉換與落檔，**不得替它補上或修改那一行**。它沒照格式輸出就是這一輪不合格。

### 2. Round 1 prompt——給素材、給立場，不給我的推理過程

Prompt 必須包含：
- 計畫文件的內容或路徑（給審查者自己 Read）
- 專案脈絡最小必要集（CLAUDE.md 路徑、本次計畫涉及的實際檔案路徑）——夠讓它查得動，不夠讓它被我的框架綁架
- 明確要求：**扮演對抗式審查者，目標是找出「會讓規則/系統靜默失效」的具體 bug，不是風格建議**；每個發現要講清楚「什麼輸入/情境下、什麼行為會出錯」；**能用工具查證的先查，不要純憑文字推理**（今晚最有價值的反駁都是查了 git log／實際跑了指令才提出的，不是憑印象）
- 明確要求結構化輸出：發現清單，每項含描述＋具體失效情境＋信心程度

**完成判準**：拿到至少一份結構化發現清單（「沒有發現」也是一種結果，不是失敗）。

### 3. 逐項回應——不是「好的我改」

對每個發現明確寫出：**接受**（要怎麼修）／**反駁**（技術理由，不是「我覺得不用」）／**部分接受**（修正版是什麼）。今晚示範過的格式：先認對方哪裡對、再指出哪裡的推論被更新的事實推翻。


**⚠ 處置本身會製造新缺陷 —— 這是這支 skill 最大的失效來源**（2026-08-23 實測：
一個 effort 九輪、45 個發現，其中 **6 個是作者在處置前一輪意見時新造出來的**，
而且**每一輪都至少一個**）。**2026-08-25 第二次實測**（另一個 effort 六輪、34 個發現，
**11 個是作者處置時造的**，同樣每輪都有）把形狀補到四種：

1. **轉述外部數字或既有結論時把方向弄反。** 例：原檔寫「把軌跡各截到 1 段，
   相符率 35%→99%」且明言那是假綠 ⇒ 99% 是 bug 的產物；轉述成「換 key 後 35%→99%，
   驗收要求 99% 不得退」——**驗收會逼實作者去保住假綠，還等於預決了那張票**。
   ⇒ **引用程式碼裡的數字，一律回原檔讀那句話的上下文，不要引摘要、不要引審查者的轉述。**
2. **改了計畫書沒改票（或反過來）。** 同一張票被連續兩輪漏改，而變更紀錄兩次都寫著
   「已處置」——**下一棒讀的是票，不是變更紀錄**。
   ⇒ **變更紀錄的處置欄必須寫「→ 改了哪幾個檔」**，只寫「接受」指不出落點，
   漏傳播就沒有任何地方看得出來。

3. **把「未決」寫成「已決」。** 前一輪的票寫「**建議**改做法」「待決」，處置時轉述成
   「做法**已由票 04 收斂為**⋯」——而且寫進審查範圍內。下一棒讀到就直接照做，
   跳過了那個還沒有人拍板的決定。
   ⇒ **引用另一張票的結論前，先看它的 `Status` 與那句話的語氣**（「建議」不是「決定」）。
4. **引用既有測試／前例時沒讀它的 stub。** 處置寫「比照既有的某支 extract 前例」，
   而那份前例把真正的寫入 helper stub 成 `() => false` ⇒ **照抄的新測試今天就會綠**，
   「先證明它會紅」永遠跨不過去。
   ⇒ **叫人「比照某個前例」之前，先讀那個前例的 stub 與固定值**，
   否則你交出去的是一個結構上不可能紅的驗收。

⚠ **還有一種不是新造、而是「殘留」**：用**檔尾加附錄**的方式修正一張票，
本文原封不動 ⇒ 同一張票兩段互相打架，而**下一棒讀的是本文**。
六輪實測裡這個形狀被指出後**又在第四張票殘留一次**（重寫清單漏了它）。
⇒ **處置要改本文，不要加附錄**；改完逐張確認本文與檔尾沒有打架。

另一個實測到的收斂訊號：**同一段文字被連續三輪抓到算錯時，不要再訂正第四次** ——
把重複的那份**整段拿掉、改成指向單一真相**。第二份計數本身就是缺陷來源。

**完成判準**：每個發現都有對應處置文字，沒有被跳過的。

### 4. 更新計畫文件＋寫變更紀錄表

比照今晚 `HARNESS_PLAN.md` 的「vN 改版紀錄」模式：新增小節，表格列「意見 → 處置」。版號往上疊（v1→v2→v3…），不覆蓋掉舊版本的推理過程——之後回頭查「為什麼是這樣設計」要找得到。

**完成判準**：計畫文件已更新；變更紀錄表存在且每列可回溯。

### 5. 開新一輪——把上下文顯式帶過去，不要假設審查者記得

**2026-07-28 首次真實 dry-run 實測推翻了這裡原本的設計**：原本寫「Claude subagent 用 `SendMessage` 續聊同一個」，實測時用 `Agent` tool 前景（`run_in_background: false`）spawn 的審查者，事後用 `SendMessage` 找它（拿呼叫時給的 description 當 name）直接被系統回絕：「No agent named '...' is reachable... use the agent ID from a **background agent's** spawn result」。前景 agent 完成當下就把結果整包回傳，沒有留下事後可續聊的身分。

**現行做法**：每一輪都是一次新的 `Agent` 呼叫，但 prompt 裡完整帶上「它上一輪的原始發現＋我逐項的回應（接受/反駁/部分接受）＋更新後的計畫版本」，明確請它「針對我的回應和新版本繼續挑，不要對已經處理過的地方重炒」。這犧牲了「同一個審查者真的記得整場對話」，換來的是**確定能動**——今晚驗證過 Agent 前景呼叫本身完全可靠（round 1 六個發現、五個獨立查證後成立）。

**未來可能的改進（沒驗證，先寫在這別當定案）**：background 模式的 spawn 結果據錯誤訊息暗示會有可續聊的身分，但這牽涉到把整套流程從「本回合內同步跑完」改成「等通知」的非同步模型，改動面比想像大，沒有為了省一點 prompt 重複就貿然改。

**⚠ 派審查者之前先記便箋，否則多輪覆核期間每個 Stop 都會被 PR-1 擋一次**
（2026-08-23 實地連撞 6 次才做這個機制）：

```
py -3 D:\.ai-harness\tools\review_inflight.py --set <計畫檔或 map> --round N   # 派之前
py -3 D:\.ai-harness\tools\review_inflight.py --clear <同一個檔>               # 蓋章之後
```

便箋記的是**派審查者當下**的 `content_hash`，與 `reviewed=` 要寫的是同一個值 ——
所以這一步順便把那個值算好了。hash 相符期間 PR-1 降成 WARN（**不是關閉**：
沒有相符的 hash 一樣蓋不出 PASSED），改動審查範圍就立刻恢復 BLOCK。

**收斂判準**（三選一達成即停）：
- 審查者明確表示沒有新的實質性發現
- 剩下的分歧只能靠實際跑測試/查真實環境解決（這時該做的是去驗證，不是再猜一輪——今晚 Step 0 spike 前那次收斂就是這樣停的）
- 達到**輪數上限 4**（今晚實際跑了 4 輪；超過通常代表計畫本身框架有問題，該回頭重想，不是繼續在細節裡繞）

**完成判準**：收斂理由三選一成立，且已明講是哪一種。

**⚠ 收斂是對「當時的實作表面」收斂，不是永久的（2026-08-23 實測）**

第二條判準（「剩下的分歧只能靠實跑與時間解決」）**會在實作落地之後失效**。
實例：`wayfinder-planning-layer` 的 map 在 Round 1 用第二條停下（rounds=1），
理由是「再審一輪只會產出沒有實作可對照的推論」——那個判斷當時是對的。
但六張票落地之後重審，**Round 2 提出 16 條、其中 10 條必須讀新程式碼或新資料才提得出來**，
全部附可重現的查證步驟，沒有一條是推論。

⇒ **effort 期間若有新實作落地，舊的「rounds=N 停」判定即失效**，該重審。
判斷方式不是「距離上次多久」，是**「上次收斂之後，有沒有產生新的可查證表面」**
（新程式碼、新資料、新的量測結果）。有就重審，沒有就別重審。

**⚠ 輪數上限 4 不是「四輪一定夠」**

同一份 map 實際跑了 **5 輪**才收斂，而且**沒有一輪在重炒前一輪**：
R2 讀票 05–10 的碼、R3 讀 R2 的改寫、R4 複驗 R3 的處置、R5 只驗 R4 那兩處。
上限的本意是擋「在細節裡繞」，不是擋「每輪都有新材料」。
**達到上限時要判斷是哪一種**：前四輪的意見有沒有互相重複？沒有的話，
上限應該讓路給「還有必須改的東西」——但**要跟 user 講，不要自己往下開**。

**2026-08-25 SG-084 的第二個樣本（Cursor GUI R1 ＋ Grok 4.6 xhigh R2–R4）**：
四輪共 19 個發現、**全數採納、沒有一輪重炒**，而且形狀非常一致——
**R2 打 R1 的處置、R3 打 R2 的處置、R4 打 R3 的處置**。也就是說，
這四輪抓的幾乎都不是原始計畫的錯，而是**作者修正意見時新造出來的錯**。
（呼應步驟 3 那條警告：處置本身是最大的失效來源。）

**這個樣本還帶出一個結構性的教訓**：連續三輪的新發現都指向同一個母題——
**作者把「實作演算法」寫死在計畫書裡，每寫一次就製造一個新洞**
（點名了一支做不到那件事的函式 → 換成一個 client 讀不到的集合 → 又把前綴 max 算錯）。
⇒ **計畫書該規定的是不變量（invariant），不是演算法。**
改成「先列 I1–I5 關票條件、演算法降級成參考實作」之後，
下一輪的發現才從「你的演算法錯了」變成「你的不變量不完備」——那是能收斂的層次。
遇到「每輪處置都被打穿」時，先問是不是寫錯了層，而不是再訂正一次演算法。

**⚠ `reviewed=` 雙 hash 的結構代價：最後一輪必須是「零改動輪」**

蓋 `ADVERSARIAL_REVIEW_PASSED` 時 `reviewed=`（派審查者當下）與 `sha256=`（蓋章當下）
不同就會被 PR-1 擋。而**照審查意見改完 in-scope 段落，兩個 hash 就一定對不上** ⇒
必須再派一輪確認沒有新意見，才蓋得出合法的章。排輪數時要把這一輪算進去。
副作用：**改 in-scope 有成本、IGNORE 區可隨意 append ⇒ 正確的話會被推去 IGNORE 區**，
被背書的那一半留著已知錯的東西。發生時要**留痕**（寫進票或紀錄表），不要默默接受。

### 5.5 一輪之內要不要分工並行（2026-08-23 實測登記·**做法未實測**）

**輪與輪之間拆不掉**：後一輪要看到前一輪的處置才有東西可挑。
**但一輪之內是可以並行的，而現在沒有並行** —— prompt 給了 N 個攻擊方向，
審查者一個一個做，牆鐘時間是它們相加。

**實測基準**（`task-identity-cost-attribution` 四輪，Claude Code ＋ Opus ＋ high）：

| 輪 | 耗時 | 工具呼叫 | 審查者 token |
|---|---|---|---|
| R1（六個攻擊方向） | 18.0 分 | 66 | 129,584 |
| R2（七個方向·攻擊改動） | 16.8 分 | 54 | 129,661 |
| R3（四個方向·判收斂） | 15.4 分 | 36 | 103,970 |

耗時**沒有隨輪次惡化**——每輪都是全新 agent、全新 context，不累積。
慢的來源是它真的在讀 1000 行以上的檔並自己寫量測腳本實跑，不是卡住。

**並行的形狀（若要做）**：N 個專科審查者同時派 ＋ **一個統合者**收斂。
牆鐘 ≈ 最慢的專科 ＋ 統合者。

⚠ **統合者不可以是主 session**。理由是這次量到的：四輪覆核裡有 **4 個發現是
「作者的處置本身製造新缺陷」**，共通形狀都是**轉述外部數字或既有結論時把方向弄反、
或漏傳播**（R1→R2 的 N1／N5、R2→R3 的 F1／F5）。跨面向統合正是這個弱點的正中央，
交給主 session 等於把最容易出錯的一步交給最會在這一步出錯的人。

⚠ **代價**：N 個專科各約 100k token ⇒ 一輪從 ~130k 變成 ~400k（**約 3 倍**）。
⚠ **會損失什麼**：跨面向的發現。R3 最重的 F4 是把「join key 不存在」「`_STAGE_RE`
沒有防誤抓的閘」「沒有票負責它」三件事串成一個發現 —— 各看一角的專科串不起來。
統合者能不能補回這一塊**沒有量過**。

**什麼時候值得**：攻擊面向 ≥4 且彼此獨立、或單輪超過 15 分鐘、或人在等。
**什麼時候不值得**：第一輪（形狀還沒摸清楚，方向切不準，切錯就是三倍成本買到更差的覆蓋）。

⚠ **這一節是設計不是結論**：序列有 4 個實測資料點，並行有 **0 個**。
說並行比較好是預測不是量測。真要改，比照 DB-1 的紀律 —— 先在一個真實 effort 上
並行跑一輪、與同一輪的序列結果對照（發現數、必改數、有沒有漏掉跨面向的那種），
再決定要不要變成預設。
