## Question

⚠ **2026-08-23 覆核 R2-N1 把這張票整個換掉了。** 原本問的是
「兩支產生器語料範圍要不要對齊、harness 算不算一個專案」——那三個選項
**建立在一個錯誤前提上**，一個都治不到病。

### 錯在哪

transcript 目錄是由 **session 啟動時的 cwd** 決定的，**不是**由「改了哪個 repo 的檔」決定。實測：

- `~\.claude\projects\D---ai-harness\`：5 個 jsonl、帶 usage 的紀錄共 **6 筆**、
  宣告段數 **0** —— 那裡幾乎沒有東西。
- ⚠ **R5 訂正證據**：最近 25 個**頂層** jsonl 的 cwd 實測是 **25/25 = `D:\IT-department`**，
  `D:\.ai-harness` **0 筆**。原本引的「23 筆」只存在於**巢狀 subagent 檔**
  （`*/subagents/*.jsonl` 最近 25 個裡 `D:\.ai-harness` 佔 15）——而那正是票 10 說
  「從來沒被讀過」的語料 ⇒ **拿它當「錢已經在面板裡」的證據會自相矛盾**。
- **正確證據是寫檔路徑**：近期三個 IT-dept 頂層 session 分別寫入 `D:\.ai-harness`
  49／34／4 次。⚠ 用錯證據，這張票很容易被答成「用 `cwd` 欄當專案維度」，
  而那對主執行緒（93% 的錢）是錯的。

⇒ **harness 的錢早就在成本面板裡，只是靜默記在 IT-department 頭上。**
把 `D:\.ai-harness` 加進白名單只會撈到那 6 筆噪音，真正的 harness 工作原地不動。
這比「顯示 $0」嚴重：$0 看得出來，錯歸屬看不出來。

### 真正要決定的

**任務的專案維度要用「transcript 落在哪個目錄」還是「這一段寫了哪些檔」？**

1. 後者本 effort 已經有工具（`effort_of_path`、`seg["written"]`），而且票 06
   正在裁決同一族的問題 —— 兩張票要一起看。
2. 一段同時寫了兩個 repo 的檔怎麼算（很常見：改 harness 順手改專案的 CLAUDE.md）。
3. 改了之後**既有的專案別金額會變動** —— 要不要先告知、要不要保留舊口徑對照。
4. 82/501 段宣告來自 AI-Projects，它們在遵循度表看得到、在成本面板沒有。
   這一半仍然成立（那是白名單差異），但它的重要性比 ①② 低。

### 施工約束（原票沒寫）

- `gen_layers.survey_projects()` 是白名單的唯一真相，而它**同時**餵「兩層對照」那張表
  ⇒ 動白名單不是局部改動，harness 會以「沒有 `.claude`、`dispatchWired=False`」
  的形狀長在兩層對照表上。
- `D:\.ai-harness` **沒有 `.claude\` 目錄**，而 `harness.config.json` 的
  `scanRoots` 靠 `.claude` 判定 ⇒ 只能走 `extraProjects`。

## 驗收錨點

改動語料／專案維度之後，**同一次 `stage_attribution()` 的 Σ任務列 == Σ階段列，
殘差恰好等於 0**（⚠ R4-M1 換錨：上一版寫「與面板總額的差額要能逐項解釋」，
而面板總額就是 ccusage、噪音底線四成，「能解釋」等於零門檻）。

## Answer

**決定（user 2026-08-23）**

| # | 問題 | 決定 |
|---|---|---|
| 1 | 專案維度用什麼 | **寫檔路徑**（這一段實際改了哪個 repo），不是 transcript 目錄（＝session 啟動時的 cwd） |
| 2 | 一段寫兩個 repo | **按寫檔次數比例拆**，不猜主 repo |
| 3 | 金額變動 | **直接變 ＋ 斷言幅度**（與票 07／10 同一個規則） |

### 實測：票說對了，量級比想像大

最近 40 個 transcript 目錄標成 `IT-department` 的 session、共 **2472 次寫檔**：

| 實際寫到哪 | 次數 | 佔比 |
|---|---|---|
| `D:\IT-department` | 1090 | 44.1% |
| **`D:\.ai-harness`** | **924** | **37.4%** |
| 其他絕對路徑（scratchpad／OneDrive…） | 458 | 18.5% |

段落層級的兩個維度對照（已上看板）：

| 專案 | 依 transcript 目錄 | 依寫檔路徑 | 差 |
|---|---|---|---|
| IT-department | 240 | 168.4 | **−72** |
| `.ai-harness` | **0** | **68.7** | **+69** |
| AI-Projects | 46 | 49.0 | +3 |

跨 repo 段落 **41/286 = 14%**。⇒ **harness 的工作一直靜默記在 IT-department 頭上**，
而票的判斷是對的：**$0 看得出來，錯歸屬看不出來。**

### 施工事實（票沒寫的兩件）

1. **`written` 只存 basename 不存路徑**（`:592` 刻意丟掉目錄）⇒ 光靠它推不出 repo。
   但完整路徑在**前一行還在手上**，而 `efforts` 正是在那裡另記一份的 ——
   **同一個位置、同一個形狀，成本一行。**
2. **harness 自己不在 `survey_projects()` 裡**：它沒有 `.claude\` 目錄，而 `scanRoots`
   靠 `.claude` 判定。所以 `repo_roots()` 必須另外把 `config.HARNESS_ROOT` 補上 ——
   **漏了它就是這張票要修的那件事本身**（harness 的錢記到別人頭上）。已有測試釘住。

### U-1（核心層不得寫死專案）

`repo_roots()` 的根清單全部從設定推：專案來自 `gen_layers.survey_projects()`
（同 `projects()` 的單一真相），harness 來自 `config.HARNESS_ROOT`。
有測試斷言 `repo_roots` 原始碼裡不出現任何專案名。
根清單**按長度遞減排**——專案可能巢狀，短根先命中會把子專案吃掉。

### 驗證方式

`tests/test_workflow_compliance.py` 新增一組（回歸網 1115 → **1130**），**三個變異各自被抓到**：

| 變異 | 變紅的測試 |
|---|---|
| 把「專案維度對照」從輸出拿掉 | 六個量測區塊都產出 |
| `repo_of_path(p)` → `None`（**接線**） | collect() 真的把 repo 記進 segment |
| 不把 harness 補進根清單 | harness 自己在 repo 根清單裡 |

另有：相對路徑回 `None`（不猜）、根之外的絕對路徑回 `None`（18.5% 本來就不該算進任何專案）。

### 沒做的

- **成本面板的專案別金額還沒切過去**。這一票交付的是**資料層＋看得見的對照**；
  真正把錢按 repo 拆需要兩條游標的結構 ⇒ **票 03**。
  ⚠ 票的驗收錨點「Σ任務列 == Σ階段列，殘差恰好 0」是對**票 03 成品**的斷言，
  這一票驗不到它（沒有任務列可比），刻意不假裝驗過。
- **`repos` 是寫檔次數不是 token 數**。比例拆分用的是「動作次數」當權重，
  那是近似 —— 真正的權重應該是那一段的 token，同樣要等票 03。

### 順帶撞到的 harness bug（與本票無關但會擋所有人）

`tests/test_harness_config.py::test_missing_field_guard` 會把 `harness.config.json`
**改名**成 `.v15bak3` 再寫一份缺欄位的假設定來驗守門。它**不是 crash-safe**：
- 中途被中斷 ⇒ 共用設定停在「缺 `scanRoots`」的狀態，**整個 harness 的產生器全部拒跑**
- 還原時**只寫回內容、沒刪備份** ⇒ `.v15bak3` 殘留，下一次跑 `os.rename` 直接
  `WinError 183`，**從此每次都紅**

實測殘骸 mtime 是 **8/16**（`os.rename` 保留 mtime，所以那就是被改名的原始檔）。
已刪除殘骸（內容與現行設定逐鍵相同，副本留在 scratchpad）。
**這個測試在多 session 環境下本身就是併發風險**：兩個 session 同時跑它必炸一個。
