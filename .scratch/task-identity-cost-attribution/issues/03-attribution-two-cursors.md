# 03 歸因資料層：兩條游標的資料結構

**Type:** prototype
**Blocked by:** 01, 02, 06, 08, 10
**Status:** ready-for-human

## Question

`gen_cost_panel.stage_attribution()` 目前是**單一游標**（`cur` 一個值追「目前生效的階段」），
而階段與任務的換手時機不同。**兩條游標的資料結構長什麼樣？**

⚠ **2026-08-23 覆核 R1 訂正了本票的驗收錨點** —— 原本寫的 fixture 不具鑑別力。

### 1. 結構

- `stages: dict` 以階段名為 key、值域是封閉的五個字；任務名是**開放字串**。
  同一份結構裝不裝得下？還是分成兩張表 ＋ 一張交叉表？
- 「任務 × 階段」交叉要不要存（存了才答得出「這個任務的錢花在哪個階段」，
  但格子數＝任務數 × 6）
- `_STAGE_RE`／`STAGES` tuple／HTML 表格列三處寫死五個階段名，
  怎麼拆才不會讓任務維度變成第四處寫死

### 2. 短形式重宣告的繼承語意（R1-F5・原本沒有票）

全域 §2 明文允許且要求「換階段重宣告一行，至少帶階段＋修改檔案兩欄」。
這種行**沒有 `模式`、沒有 `任務分類`，將來也不會有 `任務`**，實測佔 **93/501（19%）**。

pair 游標遇到它只有兩種行為：把 task 重設成 None（19% 的段落靜默掉進未標記），
或繼承（正確）。**這個分岔必須明確決定，不能讓實作自己選。**

### 3. 跨檔去重會吃掉 D3 的主場（R1-F3）

`gen_cost_panel.py:242-244` 記著：續接／分支 session 複製進新檔的訊息，
`message.id` 已被前一個檔認領 ⇒ **複製進來的宣告不會再次生效**。
對階段是小損失（每換階段就重宣告）；對任務是致命的 —— D2 說**開場只給一次**，
那一次被去重吃掉，**整個續接 session 的錢全部落進未標記**。
⚠ **R4 訂正**：`dup_skipped=20,523` **不是續接的證據** —— 它幾乎 100% 是
「同一則訊息拆成多個 content block」（`gen_cost_panel.py:180-186` 明文記載 45% 是重複）。
實測全語料 30,660 則 assistant 訊息，**跨檔重複的 message id 是 0**。
第六個坑是真的機制，但**在這台機器的語料裡從未發生過** —— 留著防它，
但別把它當常態排優先序，也別因此鬆動去重（去重拆掉會直接灌水近一倍）。

要定：任務游標要不要豁免去重？還是改由 hook 狀態檔在續接時重新注入？

### 4. §4.4 那五個坑會不會再咬

訊息去重、兩種中文編碼、兩段式解析、分母同齡、UTC 時區。
⚠ 那份清單**漏了第 6 個**（就是上面第 3 點），別把它當已窮盡。

## 驗收錨點

**鑑別性 fixture ＝「用短形式重宣告換階段」**（只帶階段＋修改檔案）。

⚠ **不是**「換階段但不換任務」—— 只要第二次宣告是完整宣告，
`(stage, task)` pair 游標算得跟兩條游標一模一樣，**兩個實作都綠**。
原本的措辭會讓下一棒造一個沒有鑑別力的 fixture，於是「先證明它會紅」
在這張票上根本做不到 —— 而這張票正是唯一被指名為變異測試錨點的。

第二個必要 fixture：**續接檔**（訊息 id 已被前檔認領）的任務歸因。
