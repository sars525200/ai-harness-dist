## 驗收錨點

**① 更新路徑要指名到人與時機**，並在收工流程裡有對應的一行。

三條都不算數，理由各不相同：

- ❌「重跑產生器，表會變」——那是**手動觸發**，證明的恰好不是「會不會被觸發」。
- ❌「`check_freshness` 回報需要更新」——它只認五個訊號（規則數／enforce／
  would-block／skill 檔數／tool 檔數），塞「任務筆數」進去會**每次跑都紅** →
  每次都得手跑 `--write-snapshot`，那是這份計畫自己在票 01 警告的 WARN 疲勞起手式。
  而且 `check_freshness` 本身沒掛在任何事件上，它是手跑的報告器。
- ❌「接進 `refresh_dashboard` 自動鏈」——它的 `SOURCES` **刻意不含 transcript**
  （含了就每回合都判定有變），而「新增一筆任務」就是一個 transcript 事件。
  **自動觸發在架構上被排除。**

**② 加總不變量**（⚠ R4-M1 換錨）：**同一次 `stage_attribution()` 的
Σ任務列 == Σ階段列（含未標記桶），殘差恰好等於 0**。

⚠ **不要拿 `cost_state.json` 的 `project_total` 當錨** —— 那個數字**就是 ccusage 的**，
而它的結構性殘差就在**四成上下**（跨期間、13 個對不上的 session、兩套定價、
subagent 語料缺口），噪音比要抓的每一個缺陷都大。「差額能解釋」在噪音大於訊號時等於零。
本票上一版正是掛著這個壞錨 —— 而且是**連續兩輪**漏改（R2-N3 一次、R4-M1 一次），
同一張票、同一種漏傳播。
