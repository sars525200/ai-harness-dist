## Question

harness **已經有**一套任務身分，而且它的設計理由正面反對 D1。
`gen_workflow_compliance.py:680-690` 的 `effort_of_path()` 從寫檔路徑
`.scratch/<effort>/` 推出工作單元，`build_tracks()`（`:692`）拿它當軌跡的 key。
它的 docstring 寫著：

> 「**為什麼用路徑推而不是加一個宣告欄位**：宣告行的格式在全域 `CLAUDE.md` §2，
> 改它影響所有專案……路徑已經帶著這個資訊，推得出來就不必要求每個人多打一欄
> ——**能推導的就不要要求人輸入**。」

D1（宣告加一欄、名稱即 key）與這條既有結論直接衝突。**必須正面裁決，不能各留一套。**

1. **兩者是什麼關係**？三個候選：
   - (a) effort 是任務的**一種推導來源**（有 effort 時優先，沒有才看宣告欄）
   - (b) 兩者獨立，各答各的問題（軌跡看 effort、成本看任務名）—— 那要說清楚
     「同一塊看板上兩種分組不一致」時讀的人該相信哪個
   - (c) 任務欄取代 effort key
2. **衝突偵測**：宣告 `任務 A` 卻寫進 `.scratch/B/` 時，現在**沒有任何地方會報錯**。
   要不要偵測？偵測到要 WARN 還是只記錄？
3. **一段碰到多個 effort** 時 `build_tracks` 退回 session key —— 任務維度要不要沿用同樣處理？
4. **docstring 那條理由要不要推翻**：「能推導的就不要要求人輸入」是對的原則。
   D1 要成立，必須說得出「為什麼這次推導不出來」（我的初步答案：非 M 級任務沒有
   `.scratch/` 目錄，而那是絕大多數 —— 但這要在票裡確認，不是假設）。

## 為什麼是一張票

第 4 條把它圍起來了，2026-08-23 已收窄範圍把它放回來。

## 驗收錨點

⚠ **2026-08-23 R3-F1**：⚠ **R4 訂正基準**：effort key 已於 2026-08-22 上線（`gen_workflow_compliance.py:692-710`
現行碼就是 effort key）⇒ **現況本來就在 35% 一帶，不是 99%**。99% 是「把軌跡各截到 1 段」
的反事實。所以正確說法是：**這張票的任何選項都不該讓相符率「回升」到 99%** —— 回升＝軌跡又被切碎。原文（`gen_workflow_compliance.py:699-702`／`:743-746`）說的是「**把現有軌跡各截到 1 段**，相符率 35%→99%」，並明言那是「沉默的綠會把遵循度翻成一片假綠」——**99% 是軌跡被切碎這個 bug 的產物**。

所以驗收**不是**守住某個百分比（那會逼人退回選項 (b) 或把軌跡再切碎，等於用驗收條款預決這張票），而是：**換 key 之後，`track_flags` 的三條判準（Execute 之前有沒有 Research、之後有沒有 Review、順序對不對）對整條序列答得出來**，且「沒有 Execute 的軌跡」不得與「合規」同一顆綠。

## Answer

**決定（user 2026-08-23）：選項 (c) —— 任務欄完全取代 effort key。**
配套決定：**一段宣告沒有「任務」欄時，同 session 內繼承上一筆；真的找不到前一筆才落未標記。**

### 裁決的實測基礎（本票原文要求「這要在票裡確認，不是假設」，以下是量到的）

用 `gen_workflow_compliance.collect()` 的真實輸出（**不是手搓 fixture**）量 515–516 段宣告：

| 量測 | 數字 |
|---|---|
| 推得出 effort 的段落 | **4 / 515 = 0.8%** |
| 軌跡 key 真的是 effort 名的 | **2 / 79 條**（其餘 77 條仍退回 session 短碼） |
| 宣告規模 **M** 的段落中推得出 effort 的 | **1 / 52 = 2%** |
| 有寫檔卻推不出 effort | 285 段 = 55.3% |
| 短形式重宣告（無模式無分類 ⇒ 永遠不會有任務欄） | **95 / 516 = 18%** |

⚠ **公平性註記**：effort key 是 2026-08-22 才上線的，只跑了一天，全機器只存在 2 個 effort。
0.8% 有一部分是「太早」，**不能拿現況直接判死一個新機制**。

**真正決定性的是上限不是現況**：`.scratch/<effort>/` 只有走 wayfinder 的 M 級工作才有，
而規模欄分佈是 M 52 / S 127 / L 79 / 待定 59 / 空 198 ⇒ **M 約佔一成**。
**就算 M 級 100% 都開 map，推導的天花板也只有 ~10%**，另外九成的工作在任何時候都推不出身分。

### 逐點回覆本票的四個問題

1. **兩者關係** → (c)。effort 不再是 key 的來源。
2. **衝突偵測（宣告 `任務 A` 卻寫進 `.scratch/B/`）** → **第一版不做**（我的判斷，非 user 裁決，可推翻）。
   理由：(c) 之後路徑不再是身分來源，這不再是「兩個 key 打架」，只是一個可能的筆誤；
   而且第一版連任務欄本身都還沒有任何資料 ⇒ 現在做偵測就是**對空集合的檢查**
   （「新裝的量測器對舊資料報零」，2026-08-23 已寫進規範的雷）。**列為第二版候選。**
3. **一段碰多個 effort 要不要沿用同樣處理** → **(c) 之後這一點消解**。任務名來自宣告、
   一段只會有一個值；實測目前「一段碰多個 effort」也是 0 段。
4. **docstring「能推導的就不要要求人輸入」要不要推翻** → **不推翻原則，但必須限定範圍**。
   `gen_workflow_compliance.effort_of_path()` 的 docstring 要改寫：那條原則成立的前提是
   「路徑真的帶著這個資訊」，而實測**九成的工作路徑不帶**。原則保留，結論作廢。

### 這張票自己的驗證方式（map 到達點條件 1 要求）

⚠ **本票的驗收錨點明文禁止「守住某個百分比」**——相符率**回升到 99% 是軌跡被切碎這個 bug 的產物**，
拿它當綠燈等於用驗收條款預決本票。所以驗的是行為不是數字：

1. **真實輸入**：測試餵 `collect()` 的實際輸出，**不得手搓 snapshot 直接餵 `build_html`**
   （本 repo 既有慣例 `test_workflow_compliance.py:265-300` 就是那樣寫的，
   那種測試「上游全壞照樣綠」）。斷言：**key 是任務名的軌跡數 > 0**。
2. **變異測試（先證明它會紅）**：把繼承那一行改成「沒有任務欄就重設為 None」，
   那 18% 短形式必須掉進未標記桶 ⇒ **測試必須變紅**。紅不了就代表這條沒被驗到。
3. **`track_flags` 三條判準對整條序列答得出來**（Execute 之前有沒有 Research、
   之後有沒有 Review、順序對不對），且**「沒有 Execute 的軌跡」不得與「合規」同一顆綠**。
4. **不得讓相符率回升到 99%**（見上）。
