## Question

`gen_workflow_compliance.py` 的 `FIELD["cls"]` 已經在解析「任務分類」並存進 segment
（`:539`），但**全 harness 零消費者**。R1 覆核獨立確認：全 repo grep 除了
`tests/test_workflow_compliance.py` 的 fixture 之外零讀取點
（`gen_todos.py` 那幾個 `"cls"` 是 CSS class，不同的東西）。D6 要這一批救活它。

1. **值域**：沿用本專案 `[UI|DB|邏輯|文件|devops]`，還是跨專案通用集？
   ⚠ harness 是跨部門共用層，值域寫死本專案五個字就是下一個「換部門還成立嗎」。
   要不要由各專案的 `PROJECT_CONTEXT.md` 宣告（同「維運腳本來源」慣例）？
   ⚠ **正規化不可跳過**（R1 實測）：203 段有值，值域實際有 **30 種寫法** ——
   `[UI|邏輯]` 與 `[UI｜邏輯]` 是兩個不同字串、`devops` 與 `[devops]` 也是。
   不正規化，消費端會把同一類拆成好幾格。
2. **消費端放哪**：獨立一張表，還是併進任務那張表當一欄？
3. **未填的比例要不要顯示**（203/501 有值 ⇒ 近六成沒填）
4. **同一任務前後段分類不一致**時以哪個為準，還是照實顯示「混合」？

## 驗收錨點

⚠ **2026-08-23 覆核 R1-F14 訂正**：驗收**不是 grep**。

`grep` 只證明呼叫點存在於原始碼，證明不了執行期會走到。若消費端寫成
`if seg.get("cls"):`，在 **219/375（58%）** 的段落上那個分支根本不進去 ——
**grep 綠、畫面空**，而那正是死欄位本來的病。

正確形式是**變異**：拿掉消費端，要有一支測試變紅。

### 為什麼值域是 per-project 而不是一份全域清單

`task_classes()` 回 `{專案名: [值...]}`，專案清單沿用 `projects()` 的單一真相
（`gen_layers.survey_projects()`）。理由：這個面板**同時呈現多個專案的宣告**，
而「UI」對 IT 資產平台與對別的部門可以是不同的東西。
某個專案沒宣告就不在 dict 裡 —— 對新部門來說那是**合法狀態**，不是環境壞掉。

### 拆標籤 vs 組合當一格：用數字決定的

| | 種類數 | 長尾 |
|---|---|---|
| 原始寫法 | **30 種** | `[UI\|邏輯]` 與 `[UI｜邏輯]` 各自成格 |
| 組合式（正規化後） | 19 種 | 其中 **10 種只出現 1~4 次** |
| **拆成標籤** | **7 種** | 5 種在值域內 ＋ 2 種規範外 |

多標籤佔 **78/206 = 38%**。原貌沒有遺失 —— segment 的 `raw` 裡還在。

的訊號，靜靜吃掉就看不見了。

### 驗證方式（票的驗收錨點：**不是 grep，是變異**）

票原文：「grep 只證明呼叫點存在於原始碼，證明不了執行期會走到。消費端若寫成
`if seg.get("cls"):`，在 6 成的段落上那個分支根本不進去 —— **grep 綠、畫面空**。」

**實跑變異**：把 `b35` 從 `build_html` 的 join 拿掉（`task_classes()` 與 `split_cls()`
**都還在**，grep 照樣命中）⇒ **4 條測試變紅**：

- 遵循度面板真的有「任務分類分佈」這一區
- 快照裡的 `[devops]` 有被拆成標籤並渲染出來
- 未填單獨列出來
- 五個量測區塊都產出（節數守門，4→5 同批更新）

**非 vacuous 守門**：另加一條「真實語料裡確實有任務分類可拆」（實得 291 個標籤）。
沒有它，上面那些在語料變空時會一起假綠 ——「新裝的量測器對舊資料報零」
跟「一切正常」在畫面上長得一樣。

回歸網 1102 → **1113**。

### 沒做的

- **同一任務前後段分類不一致的處置**（票 §4）：`任務` 欄語料為 0，現在做是對空集合設計。
  留給票 05。
- **值域外的值不阻擋、不警告**，只在畫面標「規範外」。DECL-1 側零改動（同票 01 決策二）。
- **其他專案沒宣告值域**（`AI-Projects`）：它的標籤會全部落進「規範外」。
  這是設計上的正確行為（沒宣告＝沒有值域可比），但那個專案要用這一區就得自己補一節。
